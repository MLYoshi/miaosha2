## 4. 瓶颈分析

1. **稳定容量边界 ≈ 400~500 RPS**：500 RPS 档出现 639 次 `dropped_iterations` 且 max 延迟 2.02s，说明到达率已贴近本机单机处理上限；≤400 RPS 完全平稳（p95 ≈ 9ms、0 失败）。
2. **瓶颈在 backend 受理线程路径，不在数据层**：
   - MySQL（QPS 413、无慢查询）、Redis（ops 598）极度空闲；
   - Kafka 无消费积压（lag 0）；
   - backend CPU 峰值 184.7%、线程峰值 148，长尾 2.02s 指向 `send().join()` 阻塞发送——500 RPS 下 Tomcat 200 线程排队，单线程等待 Kafka broker 确认即出现秒级尾部。
3. **Kafka 容器 CPU avg 87.9% / max 330%**：Mac 上 Docker 单节点 KRaft Kafka 的常见开销；因 lag 全 0，不构成容量瓶颈，但需在优化复测时观察其是否随吞吐线性恶化。

## 5. 结论与待验证假设

- 基线已建立：500 RPS 下 p95 9ms、0 失败、可稳定运行；数据层余量极大，瓶颈在受理线程/发送阻塞路径。
- 待验证假设（一次只改一处，复测对比）：
  1. 受理路径去掉阻塞发送（`send().join()` → 异步/回调），预期消除 2s 长尾、dropped 归零；
  2. 不动代码前提下，先调 Tomcat 线程池（200 → 500）二分定位「线程不够」vs「发送阻塞」的贡献占比。
